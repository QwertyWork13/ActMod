Section 1: One-Way Analysis — The First Test for Any Variable

Before putting a variable into your model, you need to SEE if it has any relationship with claims. A one-way analysis is the simplest check: group your data by the variable, calculate the actual loss rate in each group, and plot it. If the bars/line show a clear pattern → the variable has signal. If it's flat → useless, don't include it.

What Exactly Is a One-Way Plot?

For each candidate variable, you ask: "Do policies with different values of this variable have different loss rates?"

How to Do One-Way Analysis in Python — Full Code Walkthrough

# ══════════════════════════════════════════════════════════════
# ONE-WAY ANALYSIS — Complete Python Code
# ══════════════════════════════════════════════════════════════

import pandas as pd
import numpy as np
import matplotlib.pyplot as plt

# Step 1: Load your data
df = pd.read_csv("construction.csv")

# Step 2: Create the "loss rate" — this is what we're analyzing
# Loss rate = total claims / total exposure (for each group)
df['loss_rate'] = df['claims'] / df['TradeExposureUSD_Inflated']
Why loss rate, not raw claims? Because a $1B company will naturally have more claims than a $1M company. Dividing by exposure normalizes for size, so we're comparing apples to apples. Without this, the one-way plot would just show "bigger companies have more claims" (obvious and useless). 
# Step 3: One-way for a CATEGORICAL variable (country)
def one_way_categorical(df, variable, target='claims', exposure='TradeExposureUSD_Inflated'):
    """
    Creates a one-way analysis for a categorical variable.
    
    Parameters:
    -----------
    df : DataFrame with your policy data
    variable : string, the column name to analyze (e.g., 'country_group')
    target : string, the claims column
    exposure : string, the exposure column (for normalizing)
    """
    
    # Group by the variable, sum up claims and exposure in each group
    grouped = df.groupby(variable).agg(
        total_claims=(target, 'sum'),           # Total $ claims in group
        total_exposure=(exposure, 'sum'),        # Total $ exposure in group
        policy_count=(target, 'count'),          # Number of policies
        claim_count=(target, lambda x: (x > 0).sum())  # Policies with claims
    ).reset_index()
    
    # Calculate metrics
    grouped['loss_rate'] = grouped['total_claims'] / grouped['total_exposure']
    grouped['frequency'] = grouped['claim_count'] / grouped['policy_count']
    
    # Sort by loss rate for visual clarity
    grouped = grouped.sort_values('loss_rate', ascending=False)
    
    # Plot
    fig, ax = plt.subplots(1, 1, figsize=(10, 5))
    bars = ax.bar(grouped[variable], grouped['loss_rate'], 
                  color='#2980b9', edgecolor='#1a5276', alpha=0.8)
    
    # Add volume labels on top of each bar
    for bar, count in zip(bars, grouped['policy_count']):
        ax.text(bar.get_x() + bar.get_width()/2, bar.get_height(),
                f'n={count:,.0f}', ha='center', va='bottom', fontsize=9)
    
    ax.set_title(f'One-Way Analysis: Loss Rate by {variable}', fontsize=14, fontweight='bold')
    ax.set_ylabel('Loss Rate (Claims / Exposure)')
    ax.axhline(y=df[target].sum() / df[exposure].sum(), 
               color='red', linestyle='--', label='Portfolio Average')
    ax.legend()
    plt.tight_layout()
    plt.show()
    
    return grouped

# Run it:
result = one_way_categorical(df, 'country_group')
print(result)
Line-by-line breakdown:
df.groupby(variable)Split the data into groups (one group per country)
.agg(...)For each group, calculate sum of claims, sum of exposure, count of policies
total_claims / total_exposureThe loss rate — how many $ of claims per $ of exposure
ax.axhline(...)Draws a horizontal line at the portfolio average — so you can see which groups are above/below average
f'n={count:,.0f}'Shows volume (number of policies) on each bar — crucial for judging credibility

One-Way for CONTINUOUS Variables

# Step 4: One-way for a CONTINUOUS variable (exposure)
def one_way_continuous(df, variable, target='claims', exposure='TradeExposureUSD_Inflated',
                       n_bins=10):
    """
    Bins a continuous variable and plots loss rate by bin.
    
    For exposure, we use LOG bins because exposure is heavily skewed.
    """
    
    # Create log-spaced bins (equal width on log scale)
    df['_bin'] = pd.qcut(df[variable], q=n_bins, duplicates='drop')
    
    # Or for log-scale binning:
    # df['_log_var'] = np.log10(df[variable])
    # df['_bin'] = pd.cut(df['_log_var'], bins=n_bins)
    
    grouped = df.groupby('_bin').agg(
        total_claims=(target, 'sum'),
        total_exposure=(exposure, 'sum'),
        policy_count=(target, 'count'),
        avg_variable=(variable, 'mean')
    ).reset_index()
    
    grouped['loss_rate'] = grouped['total_claims'] / grouped['total_exposure']
    
    # Plot: line chart for continuous
    fig, ax1 = plt.subplots(figsize=(10, 5))
    
    # Loss rate line
    ax1.plot(range(len(grouped)), grouped['loss_rate'], 
             'o-', color='#2980b9', linewidth=2.5, markersize=8, label='Loss Rate')
    ax1.set_ylabel('Loss Rate', color='#2980b9')
    ax1.set_xlabel(f'{variable} (binned)')
    
    # Volume bars on secondary axis
    ax2 = ax1.twinx()
    ax2.bar(range(len(grouped)), grouped['policy_count'], 
            alpha=0.2, color='gray', label='Volume')
    ax2.set_ylabel('Number of Policies', color='gray')
    
    ax1.set_title(f'One-Way: Loss Rate vs {variable}', fontsize=14, fontweight='bold')
    ax1.set_xticks(range(len(grouped)))
    ax1.set_xticklabels([f'{x:.1f}' for x in grouped['avg_variable']], rotation=45)
    
    fig.legend(loc='upper right', bbox_to_anchor=(0.9, 0.9))
    plt.tight_layout()
    plt.show()
    
    # Clean up temp column
    df.drop('_bin', axis=1, inplace=True)
    return grouped

# Run it:
result = one_way_continuous(df, 'TradeExposureUSD_Inflated', n_bins=10)
Why show volume (gray bars) alongside the loss rate (line)?
A bin with only 5 policies might show a loss rate of 50% — but that's just noise (one big claim). A bin with 5,000 policies showing 8% is reliable. Always show volume alongside signal — this is the credibility concept visually.
Decision rule from one-way analysis:
✅ Include the variable IF: the bars/line show a clear monotonic or U-shaped pattern, AND the pattern makes business sense, AND each group has enough volume (>20 claims ideally).
❌ Exclude IF: all bars are roughly the same height (no signal), OR the pattern is random/noisy, OR one group dominates and the rest have tiny volume.

Section 2: What Is AIC? — Model Comparison Made Simple

AIC is like a report card for models. It rewards a model for fitting the data well (high marks for accuracy) but PENALIZES it for being too complex (deducts marks for having too many variables). The model with the LOWEST AIC is the best balance of accuracy and simplicity.

The AIC Formula

AIC = -2 × log-likelihood + 2 × k

Where:
• log-likelihood = how well the model fits the data (higher = better fit)
• k = number of parameters (variables) in the model
• -2 × log-likelihood = the "deviance" (lower = better fit)
• 2 × k = the penalty for complexity

Lower AIC = Better model
Think of it like buying a car:
• Fit (deviance) = how fast the car goes (you want MORE speed = LOWER deviance)
• Penalty (2k) = how much gas it burns (you want LESS fuel cost = FEWER parameters)
• AIC = total cost of ownership. You want the car that's fast AND efficient.

How to read this table:
• Model A → B: AIC drops by 1,392. Adding country is a HUGE improvement. ✅ Keep it.
• Model B → C: AIC drops by 5. Adding trade helps a little. ✅ Keep it (ΔAIC > 2 is meaningful).
• Model C → D: AIC drops by only 3. Borderline. Check cross-validation to decide.
• Model C → E: AIC drops by 59 but we added 17 parameters. Risk of overfitting! ⚠️ Must cross-validate.

Rule of thumb: ΔAIC > 2 is meaningful. ΔAIC > 10 is strong evidence.

How to Compute AIC in Python

# AIC COMPARISON — Step by Step in Python
# ══════════════════════════════════════════════════════════════

import statsmodels.api as sm
from statsmodels.genmod.families import Tweedie
from statsmodels.genmod.families.links import Log

# Define the Tweedie family with log link
# var_power=1.5 is the Tweedie p parameter
tweedie_family = sm.families.Tweedie(var_power=1.5, link=Log())

# ─────────────────────────────────────────────
# Model A: Exposure only
# ─────────────────────────────────────────────
formula_A = 'claims ~ log10_exposure'

model_A = sm.GLM.from_formula(
    formula_A,
    data=df,
    family=tweedie_family,
    offset=np.log(df['PolicyDurationYear'])  # offset for duration
).fit()

print(f"Model A — AIC: {model_A.aic:.0f}, params: {model_A.df_model + 1}")

family=tweedie_familyTells the model: "claims follow a Tweedie distribution" (handles zeros + positive skew)
offset=np.log(df['PolicyDurationYear'])Locks the duration coefficient at 1 — a 2-year policy gets exactly 2× expected claims
.fit()Runs the optimization (IRLS algorithm) to find the best coefficients
model_A.aicThe AIC value — lower is better
# ─────────────────────────────────────────────
# Model B: Exposure + Country
# ─────────────────────────────────────────────
formula_B = 'claims ~ log10_exposure + C(country_group)'

model_B = sm.GLM.from_formula(
    formula_B,
    data=df,
    family=tweedie_family,
    offset=np.log(df['PolicyDurationYear'])
).fit()

print(f"Model B — AIC: {model_B.aic:.0f}, params: {model_B.df_model + 1}")

# ─────────────────────────────────────────────
# Model C: Exposure + Country + Trade
# ─────────────────────────────────────────────
formula_C = 'claims ~ log10_exposure + C(country_group) + C(sub_trade)'

model_C = sm.GLM.from_formula(
    formula_C,
    data=df,
    family=tweedie_family,
    offset=np.log(df['PolicyDurationYear'])
).fit()

print(f"Model C — AIC: {model_C.aic:.0f}, params: {model_C.df_model + 1}")

# ─────────────────────────────────────────────
# COMPARE ALL MODELS
# ─────────────────────────────────────────────
models = {'A: exposure': model_A, 'B: +country': model_B, 'C: +trade': model_C}
comparison = pd.DataFrame({
    'Model': models.keys(),
    'AIC': [m.aic for m in models.values()],
    'Params': [m.df_model + 1 for m in models.values()],

"I compare AIC before and after adding the variable. If AIC drops by more than 2, it's a meaningful improvement. If it drops by more than 10, it's strong evidence the variable matters. Section 3: What Is the Gini Coefficient? — Measuring Model Discrimination

Gini answers one question: "Can this model tell the difference between risky and safe policies?"

Imagine sorting all your policies from "model says safest" to "model says riskiest." Then check: do the "risky" ones actually have more claims? If yes → high Gini (model is discriminating well). If the ranking is random → Gini = 0 (model is useless).

The Intuition

Gini Values — What's Good?

Gini RangeMeaningContext
0.00Random — model can't distinguish risks at allUseless model
0.10 – 0.20Weak discriminationModel is barely better than random
0.20 – 0.30DecentAcceptable for commercial lines with sparse data
0.30 – 0.40Good ⭐Typical for a well-built GL/construction model
0.40 – 0.50Very goodMotor, property with rich data
0.50+ExcellentRare in insurance — often means data leakage
If your Gini is suspiciously high (>0.6), check for data leakage — you might accidentally be using a variable that "knows" the outcome (like claim count as a predictor of claims, or using future information).

How to Calculate Gini in Python

# ══════════════════════════════════════════════════════════════
# GINI COEFFICIENT — Full Python Implementation
# ══════════════════════════════════════════════════════════════

from sklearn.metrics import roc_auc_score
import numpy as np

def gini_coefficient(actual, predicted):
    """
    Calculate the Gini coefficient for insurance pricing.
    
    Gini = 2 * AUC - 1 (for binary classification)
    
    For continuous claims data, we use a weighted approach:
    Sort by predicted, compute cumulative actual vs cumulative volume.
    
    Parameters:
    -----------
    actual : array of actual claims (can include zeros)
    predicted : array of model predictions (predicted claims)
    
    Returns:
    --------
    Gini coefficient (float between 0 and 1)
    """
    
    # Method 1: Normalized Gini (Lorenz curve approach)
    # Sort by predicted risk (ascending = safest first)
    order = np.argsort(predicted)
    actual_sorted = np.array(actual)[order]
    
    # Cumulative sum of actual claims (normalized)
    cumulative_actual = np.cumsum(actual_sorted) / np.sum(actual_sorted)
    
    # Cumulative proportion of policies
    n = len(actual_sorted)
    cumulative_policies = np.arange(1, n + 1) / n
    
    # Area under the Lorenz curve (using trapezoidal rule)
    lorenz_area = np.trapz(cumulative_actual, cumulative_policies)
    
    # Gini = 1 - 2 * lorenz_area
    # (lorenz_area for random model = 0.5, so Gini_random = 0)
    gini = 1 - 2 * lorenz_area
    
    return gini

# ─────────────────────────────────────────────
# USE IT:
# ─────────────────────────────────────────────
predictions = model_C.predict(df)
actual_claims = df['claims'].values

gini = gini_coefficient(actual_claims, predictions)
print(f"Model Gini: {gini:.3f}")  # e.g., 0.370
How this works step by step:
1. Sort all policies by what the model predicts (safest → riskiest)
2. Walk through the sorted list, tracking cumulative actual claims
3. If the model ranks well, the first 50% of policies (safest) should have WAY less than 50% of actual claims
4. The bigger this gap → the higher the Gini
5. Mathematically: Gini = 1 − 2 × (area under the Lorenz curve)

# PLOT THE LORENZ CURVE (Visual Gini)
# ─────────────────────────────────────────────

def plot_lorenz(actual, predicted, model_name="Model"):
    """Plot the Lorenz curve and show the Gini value."""
    
    order = np.argsort(predicted)
    actual_sorted = np.array(actual)[order]
    
    cum_actual = np.cumsum(actual_sorted) / np.sum(actual_sorted)
    cum_policies = np.arange(1, len(actual_sorted) + 1) / len(actual_sorted)
    
    gini = gini_coefficient(actual, predicted)
    
    plt.figure(figsize=(8, 6))
    plt.plot(cum_policies, cum_actual, 'b-', linewidth=2.5,

    plt.fill_between(cum_policies, cum_actual, cum_policies, alpha=0.1, color='blue')
    
    plt.xlabel('Cumulative % of Policies (sorted by predicted risk)')
    plt.ylabel('Cumulative % of Actual Claims')
    plt.title('Lorenz Curve — Model Discrimination')
    plt.legend(loc='upper left')
    plt.grid(True, alpha=0.3)
    plt.tight_layout()
    plt.show()

Section 4: Cross-Validation — The Only Honest Test

AIC and Gini on training data can lie — a model might look great on the data it was trained on but fail on new data (overfitting). Cross-validation is like a blind taste test: the model is evaluated on data it has NEVER seen. That's the only honest metric.

Why Training Metrics Lie

❌ Training-only evaluation

Model sees all data → memorizes noise → looks perfect on training → fails on new policies

Example: A model with 50 variables gets Gini = 0.55 on training. On new data? Gini = 0.25. It memorized, not learned.

✅ Cross-validation

Model trained on 80% → tested on unseen 20% → honest Gini → repeat 20 times → average

Example: Same model with 50 variables gets CV Gini = 0.28. A simpler 5-variable model gets CV Gini = 0.35. The simple model WINS.

Full K-Fold Cross-Validation in Python

# ══════════════════════════════════════════════════════════════
# K-FOLD CROSS-VALIDATION — Complete Implementation
# ══════════════════════════════════════════════════════════════

from sklearn.model_selection import KFold
import statsmodels.api as sm
import numpy as np
import pandas as pd

def cross_validate_model(df, formula, n_folds=20, family=None):
    """
    Perform K-fold cross-validation for a GLM/GAM.
    
    Parameters:
    -----------
    df : DataFrame with all the data
    formula : string, the model formula (e.g., 'claims ~ log10_exp + C(country)')
    n_folds : int, number of folds (20 is good for insurance)
    family : statsmodels family object (e.g., Tweedie)
    
    Returns:
    --------
    Dictionary with average Gini, AIC, RMSE across all folds
    """
    
    if family is None:
        family = sm.families.Tweedie(var_power=1.5, link=sm.families.links.Log())
    
    # Set up K-Fold
    kf = KFold(n_splits=n_folds, shuffle=True, random_state=42)
    
    # Storage for metrics from each fold
    gini_scores = []
    rmse_scores = []
    deviance_scores = []
    
    for fold_num, (train_idx, test_idx) in enumerate(kf.split(df)):
        # Split into train and test
        train_df = df.iloc[train_idx].copy()
        test_df = df.iloc[test_idx].copy()
        
        # Fit model on TRAINING data only
        try:
            model = sm.GLM.from_formula(
                formula,
                data=train_df,
                family=family,
                offset=np.log(train_df['PolicyDurationYear'])
            ).fit()
        except Exception as e:
            print(f"  Fold {fold_num}: FAILED — {e}")
            continue
        
        # Predict on TEST data (unseen!)
        predictions = model.predict(
            test_df,
            offset=np.log(test_df['PolicyDurationYear'])
        )
        
        # Calculate metrics on TEST data
        actual = test_df['claims'].values
        
        # Gini
        gini = gini_coefficient(actual, predictions)
        gini_scores.append(gini)
        
        # RMSE
        rmse = np.sqrt(np.mean((actual - predictions) ** 2))
        rmse_scores.append(rmse)
    
    # Average across all folds
    results = {
        'formula': formula,
        'cv_gini_mean': np.mean(gini_scores),
        'cv_gini_std': np.std(gini_scores),
        'cv_rmse_mean': np.mean(rmse_scores),
        'cv_rmse_std': np.std(rmse_scores),
        'n_folds_success': len(gini_scores)
    }
    
    print(f"\n{'='*60}")
    print(f"Formula: {formula}")
    print(f"CV Gini: {results['cv_gini_mean']:.4f} ± {results['cv_gini_std']:.4f}")
    print(f"CV RMSE: {results['cv_rmse_mean']:.0f} ± {results['cv_rmse_std']:.0f}")
    print(f"{'='*60}")
    
    return results
The critical parts explained:
KFold(n_splits=20, shuffle=True)Splits data into 20 parts randomly. Each part gets to be the "test set" once.
train_df = df.iloc[train_idx]19 folds = training data. The model ONLY sees this.
test_df = df.iloc[test_idx]1 fold = test data. The model has NEVER seen this. Honest evaluation.
model.predict(test_df, offset=...)Predict on unseen data. Must pass the offset for test data too!
np.mean(gini_scores)Average Gini across all 20 folds = the final honest metric.

formulas = {
    'A': 'claims ~ log10_exposure',
    'B': 'claims ~ log10_exposure + C(country_group)',

The golden rule: Pick the model with the highest CV Gini (or lowest CV RMSE). If two models have similar CV Gini, pick the simpler one (fewer variables). This is the principle of parsimony — simpler models are more stable and easier to explain.

Section 5: Why Attachment Point Is NOT a Predictor

This is a CLASSIC interview question. They'll ask: "Your policy has an attachment point of $1M. Why don't you use it as a predictor in the model?" If you get this wrong, it shows you don't understand the fundamental structure of insurance pricing.
The attachment point (retention/deductible) is the amount the insured pays before the insurance kicks in. A policy with a $1M attachment only pays claims ABOVE $1M. This is NOT a risk characteristic of the policyholder — it's a choice about the product structure. Using it as a predictor would be like a restaurant predicting how hungry a customer is based on the size of plate they ordered.

Why It Must Be Excluded — Three Reasons

🔄

1. Reverse Causality

Risky policyholders CHOOSE lower attachment points (they expect claims). The attachment doesn't CAUSE the risk — it REFLECTS the risk. Using it would create circular logic.

📐

2. It's a Product Feature

The model should estimate the GROUND-UP expected loss. Then ILFs (Increased Limit Factors) adjust for the attachment/limit structure separately. Mixing them confuses two different questions.

💰

3. Pricing Structure

Premium = Base Rate × Risk Factors × ILF(attachment, limit). The ILF handles attachment. If you put attachment in the base model, you're double-counting.

The correct pricing structure:

Premium = [Ground-up expected loss from model] × ILF(limit) × LEF(attachment)

Where:
• Ground-up expected loss = what the model predicts (as if no deductible)
• ILF = Increased Limit Factor (adjusts for policy limit)
• LEF = Loss Elimination Factor (adjusts for attachment point/retention)

These are applied AFTER the model, not inside it.

Other Variables That Should NOT Be Predictors

VariableWhy NOT a predictorHow to handle it
Attachment Point / RetentionProduct structure, not risk characteristicApply ILFs/LEFs after model
Policy LimitSame — product structure choiceApply ILFs after model
Premium (historical)Circular: premium was set by a previous modelNever use as predictor
Claim count (future)Data leakage — you can't know future claims at quote timeThis is the RESPONSE variable
Broker nameNot a risk factor — just a distribution channelMaybe use for expense loading, not technical price
Underwriter nameSelection bias — good UWs select good risksInvestigate but usually exclude
The test: "Would this variable be known at quote time, AND does it represent an intrinsic characteristic of the RISK (not the product or the process)?"

✅ Country → Yes, the risk IS physically in that country
✅ Industry (NAICS) → Yes, roofers are inherently riskier than accountants
✅ Revenue/Exposure → Yes, bigger companies have more activity to generate claims
❌ Attachment point → No, this is a product choice made AFTER assessing the risk
❌ Premium → No, this is the OUTPUT of a previous model
❌ Loss history → Tricky — can use for renewal pricing but NOT for new business model
Follow-up: "What about loss history for renewals?"
"For renewal pricing, we CAN use a policy's own loss history, but with credibility weighting. If a policy has 5 years of zero claims, we don't just assume they're risk-free — we blend their experience (Z × own_experience) with the model's estimate ((1-Z) × model_rate). The more years of data, the higher Z. This is the Bühlmann credibility approach."

Section 6: The Complete Variable Selection Decision Framework

The 5-Step Process (What You Do in Practice)

  1. Domain knowledge filter: List all available variables. Immediately exclude anything that's not a risk characteristic (attachment, limit, premium, broker). Keep obvious risk drivers (exposure, country, industry, construction type).
  2. One-way analysis: For each remaining candidate, plot loss rate. Does the pattern make sense? Is there enough volume in each group? Discard variables with no signal or counter-intuitive patterns.
  3. Sequential model building: Start with the most important variable (usually exposure). Add one variable at a time, checking ΔAIC > 2. Build up the model from simple to complex.
  4. Cross-validation: Once you have 3-5 candidate formulas, run 20-fold CV on each. Pick the one with the best CV Gini. This catches overfitting that AIC might miss.
  5. Business sense check: Show the final relativities to an underwriter. Ask: "Does it make sense that UK is 30% more expensive?" If they say "no, that's wrong," investigate — maybe the data has a quality issue.

Section 7: Tricky Interview Questions (& How to Answer Them)

These are questions that test whether you truly understand the "why" behind variable selection, not just the mechanics.

Q: "Why not use claim count as a predictor?"

Answer: "Claim count is the thing we're trying to predict (or closely related to it). Using it would be circular — like predicting tomorrow's weather using tomorrow's weather. This is called data leakage. At the time of quoting, we don't know how many claims will happen."

Q: "Why not use the broker's loss estimate?"

Answer: "The broker has incentive bias — they want a lower quote to win the business. Their estimate is not an objective risk measure. Also, it's not available for all submissions, creating missing data issues. If anything, it could be used as a secondary input for the underwriter's judgment, not in the technical model."

Q: "What if a variable improves AIC but doesn't improve CV Gini?"

Answer: "This usually means the variable helps in-sample (captures noise in the training data) but doesn't generalize. It's overfitting. I trust CV Gini over AIC in this case because CV gives an honest out-of-sample estimate. I would exclude the variable."

Q: "A variable has great signal but the underwriter says it doesn't make sense. What do you do?"

Answer: "I investigate. Often this means the variable is correlated with something else (confounded). For example, if 'number of employees' shows higher loss rates, it might just be proxying for company size (which exposure already captures). I'd check: does the effect disappear when I control for exposure? If yes, it's redundant. If it persists AND defies logic, it might be a data quality issue."

Q: "Why is Gini better than R² for insurance models?"

Answer: "R² measures how much variance is explained. For insurance data with 90% zeros and extreme skew, R² will always be low (maybe 0.05) even for a good model. Gini measures ranking ability — can the model tell risky policies from safe ones? That's what actually matters for pricing: we need to charge the risky ones more, even if we can't predict the exact dollar amount perfectly."

Q: "You have 255 columns. How do you narrow down to 5 variables?"

Answer: "First, I eliminate non-risk variables (200+ are operational/administrative — policy ID, dates, system fields). That leaves maybe 20-30 candidates. One-way analysis removes those with no signal (~15 left). Sequential AIC testing removes those that don't add value when other variables are present (~8 left). CV confirms the final 4-5 that genuinely improve out-of-sample prediction."

Q: "Why use 20 folds specifically?"

Answer: "With 35K policies and ~3,600 claims, each fold of a 20-fold CV has ~1,750 policies and ~180 claims in the test set. That's enough to compute a stable Gini. If I used 5-fold, each test fold would have 7K policies (good) but the training set would be smaller. 20-fold gives more training data per fold (95% vs 80%), which makes the fitted model more representative of the full model. It's a good balance for our data size."

Q: "What's the difference between forward selection and your approach?"

Answer: "Pure forward selection adds the variable with the best AIC improvement at each step. It's greedy — it can miss combinations where two variables are individually weak but powerful together. My approach is similar but augmented: I use domain knowledge to guide the order, I check one-way plots before adding (business sense filter), and I confirm with CV (catches overfitting). It's forward selection + human judgment + CV validation."

The "Killer" Question: "Walk Me Through How You'd Add a New Variable"

Example scenario: Your manager says "We just got deductible information for all policies. Should we add it to the model?"

Your answer (structured):
"I'd go through my standard 5-step process:

1. Is it a risk characteristic? Deductible is a product structure choice, not a risk factor. The insured CHOSE a $500K deductible — that doesn't make them riskier or safer. So my initial instinct is NO.

2. But wait — could it be informative? Actually, companies that choose HIGH deductibles might be signaling they have good risk management (self-insured retention = confidence). This creates adverse selection concerns.

3. The correct approach: The deductible affects the CLAIMS we observe (we only see claims above the deductible). So it's not that deductible predicts risk — it's that our RESPONSE VARIABLE is censored by the deductible. The right approach is: adjust claims to ground-up using development/ILF methods, then model the ground-up loss. The deductible is applied AFTER the model via Loss Elimination Factors.

4. Final answer: Don't include it as a predictor. Handle it through the pricing structure (LEFs applied after the model)."
